# Architecture — The Collector

## Overview
Two deployables. Next.js and FastAPI deploy as two Vercel Services in one project; Next.js calls FastAPI over Vercel's internal network. FastAPI owns
Supabase Postgres via async SQLAlchemy. JWT-based auth, two roles: `user`, `admin`.

```
Browser ──> Next.js (Vercel) ──internal──> FastAPI (Vercel Service) ──asyncpg──> Supabase Postgres
```

## Backend layers
`api/v1` (routers) → `services` (business logic) → `repositories` (data access) → `models` (ORM).
Cross-cutting: `core/config`, `core/security`, `core/deps`.

## Data model
```
users(id, name, email!, password, role, created_at, updated_at)
houses(id, house_number!, created_at, updated_at)
collection(id, house_id -> houses, amount, period_month, approved, created_at, updated_at)
  unique(house_id, period_month); period_month = 1st of the month the payment is for
sheet_sync_jobs(id, collection_id! -> collection [cascade], status, reason, target_cell,
                existing_value, error, attempts, created_at, updated_at)
sheet_layouts(id, spreadsheet_id, tab_name, fingerprint, layout jsonb, source ai|code, created_at)
```
(`!` = unique). All PKs uuid, timestamps timestamptz.

## Key flows
- **Login**: POST `/auth/login` → verify argon2 → JWT `{sub, role, exp}`.
- **Create user**: admin-only POST `/users`.
- **Submit collection**: user POST `/collections {house_number, amount}` → resolve/create house → row `approved=false`.
- **Approve**: admin PATCH `/collections/{id}/approve` → `approved=true`.
- **Read**: GET `/collections`.
  - user = current month only (`created_at >= date_trunc('month', now())`), sorted `created_at desc`.
  - admin = all, filter by `approved` / `house_number`. Paginated (`page`, `size`; default 10).

- **Months**: month filters and totals key on `period_month` (the month paid for). The collector's own list stays on `created_at` (what they submitted this month).
- **Sheet sync** (behind `SHEET_SYNC_ENABLED`):
  1. Approve inserts a `sheet_sync_jobs` row in the same transaction.
  2. The UI then calls `POST /collections/{id}/sheet-sync`, and a daily cron sweeps what's left.
  3. Processing a job takes a Postgres advisory lock (one sheet writer), reads the grid, and resolves the Layout Map. It reuses the saved one while the fingerprint (header row + house column) matches; otherwise the AI builds one from a redacted grid and `validate_layout` checks it.
  4. The amount is written to house row × month column. Missing future month columns are appended. A non-empty cell stops as `needs_review/conflict` until an admin overwrites it.

  ```
  approve ──> job(pending) ──> lock ─> read grid ─> layout (saved | AI→validate→save)
                                   ─> row × column ─> empty? write → done
                                                   └> not empty → needs_review (Overwrite)
  Google/AI error → failed (cron retries up to SHEET_SYNC_MAX_ATTEMPTS; admin Retry any time)
  ```

  Writes can only land on a house row × month column cell, or on the header of a month column the service just created. Totals and summaries are never written.

## Auth & RBAC
JWT bearer. `get_current_user` decodes token; `require_role` guards admin/user endpoints.
The role claim in the token is authoritative server-side; the frontend role is presentation only.

## Migrations
Alembic (async env). Initial schema migration + admin-seed data migration (env-driven credentials).
Autogenerated migrations are reviewed by hand before commit.

## Deployment
- **Vercel Services** (root `vercel.json`): `frontend` (Next.js) and `backend` (FastAPI, entrypoint `app.main:app`). Backend Env: `DATABASE_URL` (Supabase), `JWT_SECRET`, `JWT_EXPIRE_MINUTES`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `ADMIN_NAME`, `CORS_ORIGINS`.
- Frontend gets `BACKEND_INTERNAL_URL` from the service binding (`NEXT_PUBLIC_API_URL` is local-dev fallback).
- Alembic is not run on deploy; run `alembic upgrade head` against Supabase before deploying schema changes. Migrations must keep the currently deployed code working (add a server default, backfill, then constrain), and they run in one transaction, so a failed one leaves the DB untouched.
- Sheet sync env (backend): `SHEET_SYNC_ENABLED`, `GOOGLE_SERVICE_ACCOUNT_JSON`, `GOOGLE_SHEET_ID`, `GOOGLE_SHEET_TAB`, `AI_PROVIDER` (`gemini`|`grok`), `AI_API_KEY`, `AI_MODEL`, `SHEET_SYNC_MAX_ATTEMPTS`, `CRON_SECRET`. Vercel Cron hits `/api/cron/sheet-sync` daily, which forwards to the backend sweep with `X-Cron-Secret`.

## Future extension points
Sidebar built for more entries; roles centralized; house CRUD, reporting, and a possible
migration to Supabase Auth are anticipated but out of v1 scope.
